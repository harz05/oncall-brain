# Query performance

The hot queries follow `DEPENDS_ON` paths up to 6 hops, and every edge on a path must be live at the alert time
(`valid_from <= at`, and `valid_to` null or later). Written the plain way,
`MATCH p = (o)-[:DEPENDS_ON*0..6]->(s) WHERE all(r IN relationships(p) WHERE <valid at $at>)` lists every path
before it filters (`Filter` sits above `Conditional Variable Length Traverse` in the plan), so its cost grows with
the number of paths, not with the size of the graph. It first showed up on a hub-heavy test graph (292 services,
1,790 edges). This page compares what the product runs with that plain form, which is kept in
`queries/reference.cypher` as each query's `_reference`.

## What the product runs

| query | form |
|---|---|
| `blast_radius` | `oncall.live_upstream`, a user-defined function (`udf/oncall.js`): a breadth-first walk against the edge direction that follows only live edges, so a retired dependency never adds its callers |
| `path_suspects`, `recall_similar` | `oncall.live_reach`, a user-defined function: one breadth-first walk per alerting service over live edges. `path_suspects` starts from the changes in the window (`Change.at` range index), hands their services to the walk, and the walk stops once it has found them |
| `memory_suspects`, `storm_unexplained`, `depends_among` | a `shortestPath` check per candidate pair, then a validity-filtered traversal only for the pairs that need it |
| `storm_upstream` | breadth-first Cypher, one hop per `CALL {}` |
| `live_paths` | the plain traversal behind an early exit |

- **The `shortestPath` check.** These queries start from few candidates: the recalled runbooks or the given
  services. For each pair, `shortestPath((o)-[:DEPENDS_ON*0..6]->(s))` in `WITH` ignores validity, so it is a lower
  bound. If every edge on it is live at the alert time, its length is the answer. If there is none, there is no live
  path either. Only when it crosses a retired (or not yet live) edge does the query run a validity-filtered traversal
  for that pair, inside a `CALL {}` subquery. That traversal puts the validity test on the variable-length
  relationship itself (`[e:DEPENDS_ON*0..6] ... WHERE e.valid_from <= at AND (...)`), so FalkorDB applies it to each
  hop while traversing (no `Filter` operation in the plan) and never expands a retired edge.
- **Breadth-first Cypher.** `storm_upstream` expands a frontier six times, keeps only live edges and deduplicates
  each level, so each service is expanded at most once per level: about 6 x (edges in the closure) instead of one
  step per path. It reads the services that went red once, from the `Anomaly.at` range index, instead of scanning
  anomalies for every row (that scan alone takes about 38 ms at 1,000 services).
- **`live_paths`** returns up to 20 actual paths. Which 20 (among equally long ones), and in what order, is the order
  the traversal meets them. A per-hop filter would change that order, so the traversal stays plain. A
  `shortestPath` check in front returns at once when the target is not reachable within 6 hops at all.
- **Ties.** `live_upstream` returns one shortest path per caller. Among equally short ones it takes the path the
  reference's depth-first traversal meets first, by visiting callers in descending node id, which is the order
  FalkorDB 4.22 visits neighbours in.

`who_knows` (linear in people, no path enumeration), `ask`'s `search_knowledge` (full-text indexes) and
`knowledge_context` (id lookups) have no reference form. They are timed for comparison.

## Method

Generated by `python -m scripts.bench --sizes 25,100,300,1000 --reps 15`. A rerun reproduces the graphs exactly
(seeded) and the timings roughly.

- **Graphs.** 25 services is the demo graph (`datagen.generate(7)`: act 1's alert on checkout at T1, act 3's
  storm at T3). The other sizes come from `scripts/bench.py:org(n)`, seeded: a layered service map (3% edge, 5%
  gateways, 52% domain, 25% platform, 15% caches/queues/databases). Each service calls 2-14 services below it with
  Zipf-like weights, so a few caches, queues and databases take most of the fan-in. About 2% of edges are callbacks
  against the layering, so there are cycles. About 1 in 150 edges is retired before the alert, and 2 only start
  after it. On top: changes and anomalies in the 2 h alert window and 14 days of background, a 3-alert storm, past
  incidents with runbooks (3 of them point memory at a change in today's window), 4 people per 8 services, and
  docs, tickets and chat for `ask`.
- **Inputs** are what the tools pass: an incident opened on the top domain service (deep dependency closure),
  `live_paths` to the most-called shared service in its closure (the hub) and to a service it cannot reach,
  `blast_radius` on the alerting service (what triage does) and on the hub (what breaks if the database goes),
  the storm's services, the in-window suspects' services for `depends_among`, and `ask`'s search for
  "why was the postgres connection pool limit lowered".
- **Timing.** Each query runs once to warm the plan cache, then 15 times. Milliseconds are measured in the Python
  client around `GRAPH.RO_QUERY` (round trip and result parsing included), median and p95. One client, nothing else
  running against the database.
- **Same answer.** Before timing, the reference and the shipped form run on the same inputs and must return
  identical rows, in the same order when the query has an `ORDER BY`. `storm_upstream`, `storm_unexplained` and
  `depends_among` have none in either form and are compared as multisets. One intended difference: a service that
  is its own caller through a live dependency cycle gets that cycle as its `blast_radius` path, and the reference
  may list it backwards (FalkorDB 4.22 returns such a path's nodes in either direction), so either direction counts
  as equal for that row. The demo and eval graphs have no live cycles. Result: **identical in every case below**.
  `tests/integration/test_query_equivalence.py` checks the same on the demo graph at T1/T2/T3 (and before its
  retired edge was retired), on 20 eval scenarios and on the 100-service graph, sweeping every service as origin or
  target.
- **Machine.** FalkorDB 4.22.0 (native module, not Docker) on 12th Gen Intel(R) Core(TM) i5-12500H, Linux
  6.8.0-138-generic, glibc 2.35, Python 3.12.14, client and server on the same laptop.

## The two user-defined functions

Same bench graphs (`scripts.bench.org(n)` and `cases`), p50 of 5 runs, local FalkorDB 4.22.0. The rows were checked
equal to the Cypher form each time. The Cypher form is the `shortestPath` check described above.

| query | 100 svc | 1000 svc | 2500 svc |
|---|---|---|---|
| path_suspects: `live_reach` / the `shortestPath` check | 2.9 / 2.0 ms | 13.1 / 12.4 ms | 30.9 / 64.6 ms |
| recall_similar: `live_reach` / the `shortestPath` check | 2.7 / 1.9 ms | 14.2 / 31.7 ms | 35.6 / 140.8 ms |

At 100 services the function costs about a millisecond more than the Cypher. From 1,000 services up it is as fast
or 2 to 4 times faster. It walks once per alerting service: a walk per (alerting service, suspect) pair measured 8 to
17 times slower at 1,000 to 2,500 services, because the map a query carries per row has to stay small.

`live_upstream` (`blast_radius`) is checked row for row against `blast_radius_reference` but has no timing on this
page. The tables below time the breadth-first Cypher it replaced, kept as `blast_radius_cypher` in
`queries/reference.cypher`.

## Concurrency

`python -m scripts.concurrency` (`make bench-concurrency`): one client process, threads, wall-clock round trips. The
question is whether the graph stays right under load: no duplicate ids or edges, every read answered, every agent
run finding the same cause. Three things make that true, and each has a table below: unique constraints on `id` for
every label (`FalkorRepository._ensure_unique_ids`), one graph per tenant, and the per-tenant lock around agent runs
and write tools (ARCHITECTURE 3.7). The lock is a `Lease` node in the coordination graph `oncall_brain_coord`,
exclusive by a UNIQUE constraint. The same claims are tests in `tests/integration/test_concurrency.py`.

- **Machine.** FalkorDB 4.22.0 (native module, not Docker) on 12th Gen Intel(R) Core(TM) i5-12500H, Linux
  6.8.0-138-generic, glibc 2.35, Python 3.12.14, client and server on the same laptop.
- **Client.** Python threads in one process, so the client side shares one interpreter lock. Separate processes (the
  API, the MCP server, an outside agent) can only widen the gap between concurrent and sequential.

### Parallel tenants (one graph each, no shared lock)

| | wall ms | per incident p50 ms | per incident p95 ms | right cause | duplicate ids / edges |
|---|---|---|---|---|---|
| 8 tenants one after another | 914 | 109.7 | 133.1 | 8/8 | |
| 8 tenants at the same moment | 456 | 445.8 | 453.1 | 8/8 | 0 / 0 |

Eight tenants responding to the same alert at the same moment finish in half the sequential wall time. Each run
takes longer on its own because they share FalkorDB's thread pool. All eight find `chg:pgw-pool-1`, and no graph
ends with a duplicate id or edge.

### Readers while agent runs hold the tenant lock

| readers | agent runs (lock held) | reads completed | read p50 ms | read p95 ms | read p99 ms | slowest read ms | read errors |
|---|---|---|---|---|---|---|---|
| 8 | 6 in 4943 ms | 1548 | 24.9 | 50.3 | 57.4 | 68 | 0 |

Reads never take the lock. While six agent runs held it back to back on one tenant, eight readers completed 1,548
`blast_radius` / `who_knows` / `ask` calls on that tenant, p50 25 ms, none failing. A reset never leaves the graph
missing: `restore()` copies the pristine graph to a staging key and `RENAME`s it over the tenant key, and FalkorDB
moves the graph, its indexes and its constraints with the key. Deleting first and then copying made 189 of 1,344
reads fail with `Invalid graph operation on empty key` in this benchmark.
`test_reads_keep_answering_while_the_tenant_is_reset` runs 4 readers across 8 resets with 0 errors.

### Concurrent event writers on one tenant

| writers x events | wall ms | write p50 ms | write p95 ms | write p99 ms | slowest write ms | changes (expected) | anomalies (expected) | changes with != 1 CHANGED edge | duplicate ids / edges |
|---|---|---|---|---|---|---|---|---|---|
| 8 x 25 | 1226 | 1.8 | 79.6 | 167.2 | 283 | 201 (201) | 200 (200) | 0 | 0 / 0 |

Each `record_change` / `record_anomaly` call takes the tenant lock for one query, so 400 writes from 8 threads
serialise at the lock: about 2 ms for the write itself, plus a waiting tail set by how often a waiter polls. Waiters
poll every 10 ms. At 100 ms the slowest write waited 1.3 s (p99 406 ms). The graph ends exactly as written: 201
changes (200 new, plus the one id all 8 writers re-recorded, still one node with one `CHANGED` edge), 200 anomalies,
no duplicates.

### What the database enforces

| race | duplicate ids per repeat | nodes | refused writes |
|---|---|---|---|
| CREATE on 10 ids, no constraint | 10, 10, 10 | 241, 241, 241 | 0 |
| CREATE on 10 ids, UNIQUE constraint | 0, 0, 0 | 11, 11, 11 | 230, 230, 230 |
| MERGE one edge (5 keys, 600 calls) | duplicate edges: 1, 1, 0 | | |

Twelve clients racing `CREATE` on the same ten ids make ten duplicate nodes on an unconstrained label and none on a
constrained one (the losers get `unique constraint violation`). `MERGE` on one edge from 12 clients produced
duplicate edges in two repeats of three. FalkorDB's relationship constraints are keyed on a property: `DEPENDS_ON`
carries one (a UNIQUE `key`), but the board edges the agents write do not. That is why the per-tenant lock stays
around anything that writes edges. The constraints are the floor under the lock, not a replacement for it.

## Algorithms on a projection

`blast_radius` ranks the impacted services with `algo.pageRank` on a scratch graph that holds only the dependencies
live at the alert time (ARCHITECTURE 3.11): one read on the tenant graph, one `UNWIND ... MERGE` write and one
procedure call on the projection, then a delete. Measured with `python -m scripts.eval --n 40`, twice on one box,
without and with the PageRank step:

| | without PageRank | with PageRank |
|---|---|---|
| `blast_radius` queries per call, p50 ms | 8.3 | 13.2 |
| `warn_owners` queries per call, p50 ms | | 4.6 |
| `respond()` wall time per incident, p50 ms | 225.5 | 227.8 |

That is about 5 ms per `blast_radius` call on the 25-service graph (38 live edges), inside the run-to-run noise of a
whole incident. The box these two runs were made on is about 2.5x slower than the one behind the EVAL.md table.

## Limitations

- **My generator, my laptop.** The graphs are synthetic and seeded by me. Real dependency maps differ in depth,
  fan-out and cycles, and the plain form's cost depends on the number of paths, so the speedups here are an example,
  not a bound. The 292-service test graph has far more paths per service than mine: its upstream closure took
  1,653 ms, while `path_suspects` (the same closure) takes 12 ms in its reference form on my 300-service graph. Mine
  gets expensive in the other direction, into a hub (`blast_radius`).
- **Single client, warm cache, localhost.** The query timings are one client at a time, no network, the whole graph
  in memory. Load is measured only in the Concurrency section, and that section measures correctness under load more
  than throughput. Over a network the round trip is still small: on the live site (AWS box to FalkorDB Cloud Free,
  both in ap-south-1) one act 1 run made 83 queries with a median of 1.2 ms (docs/FALKORDB_NOTES.md, "Measured").
- **The `shortestPath` check falls back to a path traversal** for the pairs whose unfiltered shortest path crosses an
  edge that is not live. That traversal costs the number of live paths between the two services. With few retired
  edges this is rare. A graph where most shortest paths cross retired edges would pay it often.
- **`live_paths` still lists every live path from the origin** within 6 hops. Only an unreachable target is cheap.
  It runs once per checked suspect.
- **Tie-breaking relies on FalkorDB's traversal order.** If a later FalkorDB visits neighbours in a different order,
  `live_upstream` and the reference could pick different (equally short, live) paths. The equivalence test would
  flag it.
- **At demo size nothing is faster.** On 25 services every query takes about a millisecond either way, and the
  rewritten ones can be a fraction of a millisecond slower (more operations in the plan).
- **Equal results are tested, not proven**: on these graphs, the demo at four times, 20 eval scenarios and the
  100-service graph.
