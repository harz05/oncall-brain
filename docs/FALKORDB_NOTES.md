# What building on FalkorDB taught me

On-call Brain runs on FalkorDB 4.22.0, the C engine (module version 42200). I run it locally, in CI
(`falkordb/falkordb:v4.22.0`) and on the FalkorDB Cloud Free instance behind the live site. This page maps each
FalkorDB-specific choice in the code to the behaviour, doc page or upstream issue behind it. Issue numbers refer to
FalkorDB/FalkorDB on GitHub. "My probe" means a script I ran on a scratch 4.22.0 server, not one of the repo's tests.

## Queries, schema and coordination

| What the code does | Where | The FalkorDB behaviour behind it | Source |
|---|---|---|---|
| One graph per company (`tenant_<name>`), next to a pristine copy, a coordination graph and short-lived staging and scratch graphs | `PREFIX`, `PRISTINE`, `SCRATCH`, `_check_tenant` (adapters/falkordb/repository.py); `test_tenants_are_isolated` | One instance holds many isolated graphs, and a query cannot reach into another graph. A FalkorDB maintainer recommends one graph key per client, so that one client can never get another client's data by mistake. | Discussion #791 |
| Constraints are created only when they are missing, then waited for; schema upgrades happen on the pristine graph, never under live writes | `Coordination._setup` (coordination.py); `FalkorRepository._ensure_unique_ids`, `_ensure_edge_constraints`; `FalkorGraphStore.restore` runs `ensure_schema` on `pristine_<tenant>` before copying it (repository.py) | In the C engine, `GRAPH.CONSTRAINT CREATE` does not go through the graph's write queue. If it overlaps with writes, the server can crash or the schema can be corrupted. Creation is asynchronous: a constraint starts as `PENDING`, and a `FAILED` constraint is not enforced. So the code waits for `OPERATIONAL`. A coordination constraint that comes up `FAILED` (duplicate leases left by claims made right after a restart) is repaired: the extra nodes are removed (`coord_dedupe_leases`, `coord_dedupe_counters`, which sums counters so no count is lost), the failed constraint is dropped and built again (`test_a_failed_constraint_after_a_restart_is_repaired_without_losing_a_count`). | #3154 (open); docs: commands/graph.constraint-create |
| The UDF loader holds one lock per process and loads two libraries, mine (`oncall`) and FalkorDB's FLEX (`flex`). It runs LOAD only when a library is missing, and REPLACE only when the server's code differs from the file. It accepts both error texts for a missing function and retries once after reloading. | `ensure_udfs`, `_udf_code`, `UDF_MISSING`, `FalkorRepository._run` (repository.py); `test_a_restart_burst_loads_the_udf_library_once_and_never_replaces_code_that_matches` | Queries can fail with "Unknown function" while a library is being replaced. In my probe, two `GRAPH.UDF LOAD REPLACE` calls close together, while other clients were querying, crashed 4.22.0 with signal 11. After a Cloud Free restart, every request thread misses the function at the same moment, so a loader that always issues REPLACE fires several at once. 4.22.0 reports a missing function as either `Unknown function 'oncall.…'` or `undefined function: 'oncall.…'`. | #3357 (open) |
| The hop limit is a UDF argument. Every Cypher variable-length bound is a literal (`*0..6`, `*1..6`). | `blast_radius` calls `oncall.live_upstream(target, $at, $max_hops)` (queries/triage.cypher); `BlastArgs.max_hops`, 1 to 6 (services/tools.py); `test_the_same_question_at_depth_1_then_4` (test_algorithms.py) | A variable-length bound cannot be a parameter. On 4.22.0, `[:DEPENDS_ON*1..$depth]` fails with "Encountered unhandled type in inlined properties". The WeMakeDevs guide's demo, the same question at depth 1 and then at depth 4, is written in that form. | #3350; WeMakeDevs, "How to build an agent that reasons over a graph" |
| The blast-radius walk is a JavaScript UDF that drops dead edges while it walks | `live_upstream` (adapters/falkordb/udf/oncall.js): an edge must pass `live(e, at)` before its caller joins the next level. `tests/integration/test_query_equivalence.py` checks it row for row against `blast_radius_reference` (queries/reference.cypher). | A predicate on a variable-length path filters the paths after they are expanded. It does not stop the expansion, so the walk still enters a retired dependency's whole subtree. A UDF cannot write the graph, so the board writes stay in Cypher (`record_impacts`). A library belongs to the whole instance, not to one graph, so it is loaded once per client, not once per tenant. | #3315; docs: udfs |
| The fewest live hops is a second UDF; `shortestPath` stays where a path is listed, in a `WITH` | `live_reach` (udf/oncall.js) in `path_suspects` and `recall_similar` (investigate.cypher), checked against their `_reference` forms by test_query_equivalence.py; `shortestPath` in a `WITH` in `live_paths` and `any_path` | FalkorDB accepts `shortestPath` only in `WITH` or `RETURN` ("FalkorDB currently only supports shortestPaths in WITH or RETURN clauses"), and the pattern takes no property filter, so the shortest path it returns can run through a retired edge. `path_suspects` and `recall_similar` need only the hop count, so `live_reach` walks once per alerting service over live edges, is handed the services that changed, and stops once it has found them (as fast as the Cypher form at 1,000 services, 2 to 4 times faster at 2,500; docs/PERF.md). A walk per (alerting service, suspect) pair was 8 to 17 times slower: the map a query carries per row has to stay small. | docs: cypher/functions, udfs |
| Time windows arrive as parameters | `storm_alerts` takes `$since` and `$until`, not `a.at ± $window` (triage.cypher); `TIME_INDEXED`, `PROP_INDEXED` (repository.py); `tests/integration/test_plans.py` | FalkorDB uses a range index only when the bounds are literals or parameters. Bounds computed from a bound variable produce `Node By Label Scan`. `test_plans.py` runs `GRAPH.EXPLAIN` on every named query and fails on any scan that is not on its list of scans with a stated reason. It passes typed dummy parameters, because null parameters can give a worse plan than the real call gets. | docs: cypher/indexing/range-index ("Verifying Index Usage"), commands/graph.explain |
| Every `DEPENDS_ON` and `OWNS` edge must carry `valid_from`, and the date is part of the `MERGE` or `CREATE` pattern | `DATED_EDGES`, `EDGE_CONSTRAINTS`, `_ensure_edge_constraints` (repository.py); `ingest_services`, `ingest_depends_on` (ingest.cypher); `add_dependency`, `transfer_ownership` (events.cypher); `test_the_database_refuses_an_undated_dependency_or_owner` (test_hardening.py) | A MANDATORY constraint is checked the moment the edge is created, before any `SET` or `ON CREATE SET` in the same query runs. So `MERGE (t)-[o:OWNS]->(s) SET o.valid_from = …` is refused with "mandatory constraint violation". With the date inside the pattern, the database refuses any undated dependency or owner, whoever writes it. | docs: commands/graph.constraint-create |
| Each `DEPENDS_ON` edge has a key, UNIQUE and MANDATORY | `KEYED_EDGES`, `EDGE_CONSTRAINTS` (repository.py): `key` = `<caller>><callee>@<valid_from>`, in the `MERGE`/`CREATE` pattern of `ingest_depends_on` and `add_dependency` (which moves it with an earlier start); `backfill_dependency_keys` keys a graph from before it; `test_racing_writers_record_one_dependency_once_without_any_lock` (12 clients, no lock, one edge) | Relationship constraints exist (`GRAPH.CONSTRAINT CREATE <graph> UNIQUE RELATIONSHIP DEPENDS_ON PROPERTIES 1 key`) but are keyed on a property, and UNIQUE skips an edge that lacks it, hence MANDATORY too. A constraint built over a graph that breaks it comes up `FAILED`, so the keys are backfilled first. Retired and re-added dependencies between one pair keep apart: they start at different times. | docs: commands/graph.constraint-create |
| A seed is built on a staging graph and published whole: `GRAPH.COPY` to the pristine copy, then `RENAME` over the tenant | `seed` (services/seeding.py), `FalkorGraphStore.staging`, `publish` (repository.py) | Nothing can read or write a half-built company, which matters when the watchdog re-seeds a live site after a Cloud restart, and the pristine copy holds only seed data, never a visitor's question. The seed holds the tenant lock while it builds and publishes. | (my design; same `RENAME` behaviour as the reset below) |
| A reset runs `GRAPH.COPY` into a staging key, then `RENAME` over the tenant key | `FalkorGraphStore.restore`, `snapshot`, `_copy` (repository.py); `test_reads_keep_answering_while_the_tenant_is_reset`, `test_every_label_has_a_unique_id_constraint_that_reset_keeps_and_the_database_enforces` (test_concurrency.py) | `RENAME` is atomic and FalkorDB follows it, so readers never see the graph missing. Deleting and then copying leaves a window in which reads fail with "Invalid graph operation on empty key". `GRAPH.COPY` carries indexes and constraints, so a reset keeps them. Cloud's Write preset includes both commands. `GRAPH.COPY` forks the way `BGSAVE` does and fails with "could not fork" while another fork is running, so `_copy` retries with backoff. | docs: commands/graph.copy, cloud/operations/user-management |
| No `DUMP` or `RESTORE` anywhere | nothing in `src/` calls them | In one of my probes on 4.22.0, restoring a DUMP of a graph with indexes crashed the server (SIGSEGV in `Index_SetLanguage`). Two other probes restored indexed graphs without trouble, and the 4.22.1 release lists fixes for RESTORE crashes. I did not isolate the cause, and kept `GRAPH.COPY`. | v4.22.1 release notes (#3176) |
| Locks, throttles and the LLM budget are nodes in one graph, `oncall_brain_coord` | adapters/falkordb/coordination.py, queries/coordination.cypher | FalkorDB Cloud allows only a fixed list of commands, for every user: "Only these commands (and their subcommands) may appear in an ACL". The list has no `SET`, `GET`, `INCR`, `EVAL`, `KEYS` and no pub/sub commands. So redis-py's `Lock` and Lua rate limiters cannot run there. | docs: cloud/api-reference/database-users/overview |
| A UNIQUE constraint is the mutex | `coord_claim` runs `CREATE (:Lease {key, owner, exp})`; the UNIQUE constraint on `Lease.key` comes from `Coordination._setup`; `_taken` (coordination.py); `test_one_of_many_concurrent_claimers_wins` | A unique constraint is checked when the write commits, under the graph's write lock, and a violation rolls back the whole query. So of any number of concurrent claimers, exactly one `CREATE` succeeds. This depends on every write being a plain `GRAPH.QUERY`, which is all the app sends. In the C engine, a write inside `MULTI`/`EXEC` runs on the Redis main thread and skips the per-graph write queue. | docs: design/concurrency, commands/graph.constraint-create; #3136 |
| A counter update is a single write query | `coord_incr`; `test_concurrent_increments_are_not_lost_and_an_expired_counter_restarts` | "Only one write query executes at a time on a given graph", and each write applies completely or not at all. So `SET c.n = c.n + $by` loses no increment. | docs: design/concurrency |
| `timestamp()` is read once per query | `coord_incr` and `coord_renew` start with `WITH timestamp() AS now` | `timestamp()` is the server's wall clock in milliseconds, and it is read again on every call. In my probe, the rows of one read spanned 38 ms. Reading it once per query keeps compare-and-set consistent. Because it is the server's clock, processes on different machines agree on when a lease expires. | docs: cypher/functions |
| Graph algorithms run on scratch projections, which expire | `_criticality`, `_storm_components`, `independent_routes` (services/tools.py); `topology_at`, `project_topology`, `criticality`, `project_storm`, `storm_components` (algorithms.cypher); `FalkorRepository.scratch`, and `write`, which sets `EXPIRE` to `SCRATCH_TTL` (300 s); `test_criticality_comes_from_the_dependencies_live_at_alert_time_not_from_history` | The procedures walk every edge of the given label and type and cannot filter on a property. The tenant graph keeps retired and future `DEPENDS_ON` edges as history. `algo.pageRank` takes one label and one relationship type, with no weights and no personalised variant. In my probe, PageRank's top score was 0.016 on the whole tenant graph and 0.114 on the projection. `EXPIRE` is on Cloud's allowed list (`PEXPIRE` is not), so it drops a projection that a dead process left behind. | docs: algorithms/; #1116, #289 |
| Full-text hits are ranked in Python, and the database-side limit is set above the corpus size | `PER_LABEL = 200`, `terms()` and the coverage ranking (services/brain.py); `search_knowledge` (knowledge.cypher) | The full-text `score` counts matched query terms (an optional term scores 0); it does not measure relevance. In my probe, `'payments\|kafka\|latency'` on Message scored 5, 4, 2 and 0.276. An `ORDER BY score LIMIT` set below the corpus size could drop the best hit. The demo has fewer than 50 records per label. `terms()` keeps only `[a-z0-9]` words and joins them with `\|`, because the query string uses RediSearch syntax: `payments-gw` would mean payments AND NOT gw. The index has no stopword list, so brain.py keeps its own. | #1208; docs: cypher/indexing/fulltext-index |
| Times are stored as epoch-second integers | every `at`, `valid_from` and `start` (docs/DATA_MODEL.md); a range index on `Change.at`, `Anomaly.at` and `Alert.at` | I chose integers for a repeatable demo clock. They also stay clear of a bug where a range index on a string property answers `<` and `<=` with every row. The range-indexed time properties are numbers, and no query compares an indexed string property with `<` or `>`. | #3128 |
| `algo.betweenness` is not used | no call in queries/; docs/ARCHITECTURE.md 3.4 | The docs say that when `samplingSize` is at least the number of eligible nodes, every node is used. The 4.22.0 source (`proc_betweenness.c`) draws `samplingSize` random sources with replacement (`simple_rand(&samplingSeed) % nvals`). With `samplingSize: 10000` on the demo's 25 services, seed 42 ranked checkout first (30.0) and seed 7 ranked payments first (57.3). A score that decides which change gets blamed has to be exact. | docs: algorithms/betweenness-centrality |
| Typo-tolerant service names use FLEX | `registry.call` (agents/registry.py) resolves every service argument against the graph before a tool runs, on every surface, and refuses an unknown name with suggestions; `resolve_service` (knowledge.cypher) calls `flex.text.jaroWinkler`; FLEX 1.0.1 is vendored unmodified (udf/flex.js, MIT, FalkorDB Ltd.); `test_a_service_the_graph_does_not_hold_is_named_unknown_not_answered_about` | FalkorDB's own utility library runs inside the database as a UDF library. `kafak` gets "did you mean svc:kafka?", `chekout` gets `svc:checkout`, `database` gets no guess. A close name is only ever a suggestion, never resolved silently. | docs: udfs/flex |
| Routes that share no dependency edge use `algo.maxFlow` on the projection, every edge capacity 1 | `independent_routes` (services/tools.py), `route_count`, `project_topology` sets `cap: 1` (algorithms.cypher); `test_independent_routes_counts_live_routes_with_max_flow` | `capacityProperty` must name a property key that exists in the graph (else "'capacityProperty' does not exists key"), so the projection writes one. With capacity 1 the flow counts routes that share no edge (they may still pass through one service): checkout reaches payments-gw one way only, through payments. | docs: algorithms/maxflow; my probe |
| The Plan button (and the `query_plan` tool) profiles reads only | `FalkorRepository.plan` (repository.py): `GRAPH.PROFILE` for a named query with no write clause, `GRAPH.EXPLAIN` for any other; coordination queries are refused; `test_query_plan_profiles_a_read_explains_a_write_without_running_it` | PROFILE executes the query (writes included), EXPLAIN only plans it. Each trace step also shows FalkorDB's own numbers from the reply: `run_time_ms` (time inside the database, next to the app's round trip), `cached_execution` (plan cache) and the write counts. | docs: commands/graph.profile, graph.explain |
| Facts carry two times | `recorded_at` (`timestamp() / 1000.0`, transaction time) next to `at` / `valid_from` (valid time) on what `record_change`, `record_anomaly`, `add_dependency` and `open_incident` write; `learned_late` (comms_memory.cypher) in the outcome; `test_a_change_reported_after_the_incident_opened_is_used_and_marked_learned_late` | A change CI/CD reports after the incident opened is used by the agents and listed as learned late, so the graph never quietly rewrites what was known when the incident started. `learned_late` lists the suspect changes and the anomalies on the evidence paths, inside the alert window, that the graph learned after the incident opened. `timestamp()` is the server's clock, so every process agrees on it. | docs: cypher/functions |
| Reads go as `GRAPH.RO_QUERY` with a timeout; writes get no timeout | `FalkorRepository._send` passes `ro_query(..., timeout=read_timeout_ms)`, 3000 ms by default (config.py); `_DB_BUSY` returns a 503 with `Retry-After` (api/app.py); `test_read_tools_cannot_write`, `test_a_runaway_read_is_cut_off_by_the_read_timeout` | `RO_QUERY` refuses writes, so a read tool cannot write by mistake. ## FalkorDB Cloud Free, and what the code does about it

| Fact | Source | What the code does |
|---|---|---|
| Every user is limited to a fixed command list: no `SET`, `GET`, `INCR` or `EVAL` | docs: cloud/api-reference/database-users/overview | Coordination lives in a graph (above). Scratch graphs use `EXPIRE`. Resets use `GRAPH.COPY` and `RENAME`. |
| "The Free Tier has no persistence and no backups." | docs: cloud/tiers/free | `serve.tend` runs once a minute. `Coordination.recheck` puts the coordination constraints back, and `reset` re-seeds the demo company if its graph is missing. The first query that misses the UDF reloads it (`_run`). This is tested in `test_a_restarted_database_heals_within_one_tend`. A restart still loses what visitors taught the live site, and docs/SECURITY.md says so. |
| "Free instances that aren't utilized for 1 day will be stopped, and deleted after 7 days." | docs: cloud/tiers/free | The container health check calls `/api/health` every 5 s (docker-compose.yml): one PING and two `GRAPH.RO_QUERY` reads of coordination counters. `tend` adds `GRAPH.LIST` and a constraint listing once a minute. The docs do not define "utilized", so I do not know whether reads count. A stopped instance needs someone to press Start in the console. |
| 100 MB of RAM, which is also the maximum dataset, shared by every graph on the instance | docs: cloud/tiers/free | On the live box, `MAX_TENANTS=8` (two graphs per company; docs/DEPLOY.md F). Scratch graphs expire after 300 s. |
| No TLS on Free | docs: cloud/console/connect | `FALKORDB_URL` uses `redis://`, and docs/SECURITY.md says what travels unencrypted. A paid tier with TLS takes `rediss://`. `FalkorGraphStore` sets `ssl_check_hostname=ssl`, because the falkordb client turns hostname checking off by default. |

## Open questions I would file upstream

These are notes. I have not filed them.

1. **Concurrent `MERGE` of one edge made duplicates.** The concurrency page says "Only one write query executes at a
   time on a given graph" and "Write queries always see the most recent committed state". In my race, 12 clients
   ran `MATCH (a:Probe {id:'a'}), (b:Probe {id:'b'}) MERGE (a)-[:R {k: $k}]->(b)` as plain `GRAPH.QUERY` calls (5
   keys, 600 calls; `edge_race` in scripts/concurrency.py). Two of the three repeats made duplicate edges
   (docs/PERF.md). A 12 x 200 variant made 3 to 6 duplicates, and one 12 x 100 run made none. With a range index on
   the edge key, or a UNIQUE edge constraint, I saw no duplicates. I have not isolated the cause. The next steps
   are a single-thread run, the same race without `{k}`, and waiting for the index before racing. The code does not
   depend on the answer: node ids have UNIQUE constraints, `DEPENDS_ON` has a UNIQUE key, and agent runs hold a
   per-tenant lease.
2. **The betweenness docs and code disagree.** The docs say every eligible node is used once `samplingSize` reaches
   the node count. The code samples with replacement, so results change with `samplingSeed` and never become exact
   (see the table above). Either the algorithm should run exact Brandes in that case, or the docs should say the
   result is always a sample.
3. **The fuzzy full-text example does not work as documented.** The docs give `'%Jangle%1'` (distance 1). On 4.22.0
   it is read as the fuzzy term `%Jangle%` AND the literal word `1`: it matched only after I added "1" to the
   title, and `'%Jngle%2'` matched nothing. The forms that work use one `%` pair per unit of distance: `%term%`,
   `%%term%%`, `%%%term%%%`. The product does not use fuzzy full-text search.

## Limits I know about

- `live_upstream` breaks ties by internal node id (`q.id - p.id`) so that its order matches the Cypher form's. The
  docs say `id()` values can be reused after deletes, so the order of equal-length paths could change after a
  delete.
- I have tested only the 4.x C engine (4.22.0, and 4.18.3 through the falkordblite wheel). I have not run the 6.x
  Rust engine, which has been the `latest` image since 6.0.0.
