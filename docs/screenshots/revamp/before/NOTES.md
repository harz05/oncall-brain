# Before screenshots (design revamp), Oct 18 2026

Captured with headless Chrome (puppeteer-core) against the running server at http://127.0.0.1:8000/web/.
Viewports: 1440x900, 768x1024, 390x844. Files are `<state>-<width>.png` (what fits the viewport, i.e. the first screen).
Extras: `-full` = full page at 768/390 (there the page scrolls); `-scrolled` = 1440 with the inner panel scrolled to the bottom
(on desktop the shell is fixed-height and the panel scrolls, not the page).

Where each state came from:
- `acme` (live, default tenant): landing, simulate-menu, answer, why, ask-empty, ask-answered, ask-answered-graph (phone/tablet only), connect.
- `shots` (live, `?tenant=shots`, has 1 confirmed + 2 open incidents, one a 3-alert storm): inbox-with-incidents, answer-confirmed, answer-storm.
- `?offline=1&step_ms=1000` (recorded replay from web/fixtures, no database): working, working-why, answer-just-confirmed, answer-learned.
  Confirm was clicked only here (it hits fixture `resolve.json`). Nothing was confirmed, rejected or reset on a live tenant.
- `?tenant=nope` (unknown tenant): error, empty.
- No live agent run was triggered. The only live model call is Ask ("who owns kafka?"), once per width.

## Console errors

- `error` / `empty` (`?tenant=nope`): one `Failed to load resource: 404` per load (GET /api/tenants/nope/alerts). Expected: it is the error the toast reports.

## What a first-time on-call engineer sees in the first 10 seconds

**Landing / inbox.** Desktop: a product name, a one-line tagline in the header, and a hero that reads like a landing page ("What broke, why, who's paged, and the fix.") with a big orange "Simulate an incident: refunds is slow" button. The thing that matters to an on-call engineer, the incident list, is a narrow left column with one truncated row; nothing tells them to click it. The hero's CTA and the header's "Simulate an incident" button do the same thing. "Connect your alerts" and the three how-it-works cards read as marketing. Footer text ("FalkorDB connected · steps chosen by Claude Opus 5.5 · Acme (demo company)") is internal jargon. On tablet/phone the tagline is gone (hidden below 1280px) and the header wraps "On-call Brain" onto two lines at 390; the inbox and its status footer now sit above the hero, so the screen opens on a list the user cannot yet interpret, then a marketing headline. When every scenario has been run, the orange primary CTA becomes "All demo incidents handled. Reset demo company", which looks like the main action but wipes the demo graph.

**Answer (open incident).** Within a few seconds the structure works: status pill, title, a boxed "Likely cause" with the service in orange, a confidence chip, green "Confirm cause", then What broke / Who's paged / Fix. What confuses: the stored acme incident is titled "2 alerts, 1 incident" with the storm line "1 alerts, 1 incident" (data quirk plus wrong plural); "Seen something like this" appears above the verdict with no visual rank; the right rail ("What a change log alone would blame", "WRONG" badges) is an evaluation artefact, not something an on-call needs; the confidence chip is a full sentence inside a pill. On phone the first screen is header + back button + title + Answer/Show me why toggle + memory line, and the cause only appears below that; the Confirm/Wrong bar is sticky at the bottom, which is good. The confirmed state is clear (green card, "Confirmed by you") but Fix still says "No runbook for this yet. Confirm the cause…" on a stored confirmed incident, which contradicts the status.

**Working.** Clear enough: three role cells with done/working/waiting, a spinner sentence in the agent's first person, skeleton placeholders where the answer will land, "Skip to answer". Readers must know what "hypothesize_from_memory" means (raw tool names leak into the live line). On phone the three cells fill the screen and the user cannot see that an answer is forming below.

**Show me why.** Desktop: a dense dependency graph with an orange path and a long scrollable list of 20 step cards; each card mixes a human question ("Who depends on payments-gw?"), a `snake_case` tool name, a model badge and a WHY line, so it reads as a debug trace. There is no cue that clicking a step highlights it on the graph. On phone the graph is a 45vh strip that crops the cause path; the legend takes two lines; the steps come after. Nobody is told what to do with this view in 10 seconds; it is for the curious, not the paged.

**Ask.** Desktop: a chat column with six example chips and a big whole-company graph on the right whose "Incident only" button does nothing in this context. After a question the answer is a readable sentence with typed source chips and a scoped graph: this is the best-explained screen. Phone/tablet: a large empty dark area between the chips and the input, and the graph is behind a "Show on graph" button that opens it below the fold, so nothing visibly happens on tap.

**Connect.** A six-card integration page with copyable curl, plugin and env snippets and status pills. Engineers understand it, but it is a wall of equal-weight cards with no order of operations ("do this first"), and the deployment-specific text (127.0.0.1) is visible in the demo.

**Simulate menu.** A dropdown (bottom sheet on phone) listing three scripted scenarios with one-line stories and Simulate buttons, a custom-alert form and a "Reset demo company" button next to the planner line. Understandable, but the dangerous reset sits in the same menu as the primary demo action.

**Error / empty.** The unknown-tenant toast is a raw API sentence (`POST /api/tenants/nope/reset seeds it`) placed over the headline (fully covering it on tablet/phone); it disappears after 10 s, leaving a page whose primary button says "All demo incidents handled" when nothing was loaded. The real empty-inbox copy ("No open incidents. Alerts from your monitoring land here. Simulate one, or connect your alerts.") is good but on phone it is below the fold.
