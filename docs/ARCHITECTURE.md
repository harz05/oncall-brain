# Architecture

On-call Brain is a small team of incident agents (triage, investigator, comms) that work on a FalkorDB graph of a company: its services, dependencies, owners, on-call shifts, changes, tickets, chats and past incidents. The agents share one incident "board" that lives in the graph. When a human confirms a fix, it becomes memory that the next incident recalls.

This document follows the usual system-design order: requirements, high-level design, deep dive, scale and reliability, trade-offs. It names the real modules and functions, so you can open the file next to each section.

Related documents:
- [DATA_MODEL.md](DATA_MODEL.md): every label, relationship, property and index.
- [QUERIES.md](QUERIES.md): every named Cypher query and its purpose (generated by `make docs`).

## 1. Requirements

### 1.1 Functional

| # | The system must... | Where it happens |
|---|---|---|
| F1 | Open an incident for an alert and make it the shared board for all agents. | `open_incident` tool, `open_incident` query |
| F2 | Find who is hurt: every service that depends on the alerting service, directly or through other services, using only dependencies that existed at alert time. | `blast_radius` tool and query |
| F3 | Find and page whoever is on call for the owning team at alert time. | `page_on_call`, `on_call_for` |
| F4 | List suspects: changes (deploys, config changes) in the 2-hour window before the alert on any service the alerting service depends on. Also list the newest changes anywhere, so the graph can refute what a flat change log would blame. | `propose_hypotheses`, `path_suspects`, `recent_changes` |
| F5 | Test each suspect against graph facts and record a verdict with a reason. | `check_hypothesis`, `domain/verdict.py` |
| F6 | Hand off between roles through the graph, not through Python variables. | `incident_board`, `log_step`, `agents/loop.py` |
| F7 | Post a status update that names impact, cause, ruled-out suspects, who was paged, the runbook and the sources. | `post_update`, `domain/update.py` |
| F8 | Turn a human-confirmed fix into memory, and recall it on the next similar incident. | `resolve_incident`, `recall_similar`, `hypothesize_from_memory` |
| F9 | Answer company-brain questions with sources: who knows a service, where a change came from. | `who_knows`, `change_story` |
| F10 | Explain every answer: the reason for each step, the Cypher it ran, the rows, the timing, and the graph ids to highlight. | `TraceStep`, `QueryRun`, `Highlight` |
| F11 | Expose the same tools to the agent loop, an MCP client and the HTTP API. | `agents/registry.py` |
| F12 | Keep each tenant's data in its own graph, and let the demo reset to a pristine state. | `FalkorGraphStore`, `GRAPH.COPY` |

### 1.2 Non-functional

Measured on this machine (laptop, FalkorDB v4.22.0 on redis 8.10.2, seeded demo graph: 217 nodes and about 400 relationships before any incident runs).

| NFR | Target | Measured | How to check |
|---|---|---|---|
| Latency per graph tool | < 50 ms | typical step 1 to 3 ms of database time; slowest step is `propose_hypotheses` at about 9 to 15 ms (5 queries); slowest single query about 7 ms (`recent_changes`) | `make demo` prints queries, rows and ms per step |
| Latency per incident | < 1 s with the deterministic planner | act 1: about 140 ms wall time for 17 steps, 63 queries (16 of them board reads); act 2: about 45 ms. Over 200 random eval scenarios: p50 55 ms, p95 87 ms. `make demo` (seed, three incidents, three resets) runs in about 0.75 s | `time make demo`, `make eval` |
| No LLM key needed | demo, tests, UI and MCP all work without one | yes: `MockProvider` (the deterministic planner) is the default | `GET /api/health` shows `planner` |
| Read safety | read tools cannot write | every read goes through `GRAPH.RO_QUERY`; FalkorDB rejects writes | `test_read_tools_cannot_write` |
| Tenant isolation | no tenant can see another's data | one graph per tenant | `test_tenants_are_isolated` |
| Idempotency | re-seeding and re-running are safe | `MERGE` on stable ids everywhere | `test_seeding_is_idempotent`, `test_agent_steps_persist_in_the_graph_and_respond_is_idempotent` |
| Failure behaviour | FalkorDB down gives a clear error, not a hang. A bad LLM reply never breaks a run | API returns 503 (`/api/health` still answers with `falkordb: false`). LLM errors fall back to the deterministic planner | `api/app.py` exception handlers |
| Repeatability | the demo gives the same result every run | fixed seed, pinned demo clock (`datagen.T1`), epoch-int timestamps, reset from a pristine copy | `make demo` exits non-zero if the story breaks |

### 1.3 Constraints

- Hackathon rules: FalkorDB must be the primary database and do real work. Data must be synthetic. AI assistance must be disclosed ([AI_USAGE.md](AI_USAGE.md)).
- The dev machine has glibc 2.35, so the `falkordblite` wheel (needs glibc 2.39) does not install. We run FalkorDB's official rhel8 module build on a self-built redis (see [ADR-002](decisions/ADR-002-stack.md)).
- No `docker pull` on the dev machine (the internal disk is nearly full). Everything lives on the external drive. Docker files are shipped for judges but not run locally.
- No LLM key is available, so every feature must work on a deterministic planner.
- One builder (plus AI), hours not weeks. Least code that works.

How data flows, in one paragraph: a client asks to respond to an alert. `respond()` opens the incident, then runs the roles in turn. Before every decision the loop reads the incident board from FalkorDB. The planner (or an LLM) looks only at that board and picks the next tool. The tool runs named Cypher through the `GraphRepository` port, writes its findings back to the graph, and returns a `ToolOutput` with a summary, data, the queries it ran and the ids to highlight. The loop records the step in the trace and as an `AgentStep` node. The next decision sees it because it reads the board again.

### 3.2 Ports and adapters

| Port (Protocol) | Methods | Adapter today | Test double / alternative |
|---|---|---|---|
| `GraphRepository` | `read(name, **params)` (RO), `write(name, **params)`, `ensure_schema()`, `tenant` | `FalkorRepository` | Integration tests use a real FalkorDB with throwaway tenants |
| `GraphStore` | `tenant()`, `exists()`, `snapshot()`, `restore()`, `drop()`, `tenants()` | `FalkorGraphStore` | |
| `LLMProvider` | `decide(role, board, tools) -> Decision`, `name` | `MockProvider` (default), OpenAI-compatible, Anthropic | Planner unit tests call `next_decision` on plain dicts |

Two details matter:
- Queries are addressed by name, not by text. `read("live_path", origin=..., target=..., at=...)` loads the statement `// name: live_path` from `queries/investigate.cypher`. Cypher text exists only in `.cypher` files. Parameters are always passed separately, so user input is never formatted into Cypher.
- `read()` uses `GRAPH.RO_QUERY`. FalkorDB itself rejects any write inside it ("graph.RO_QUERY is to be executed only on read-only queries"). So a read tool cannot write even if its Cypher is wrong. This is enforced by the database, not by our code.

### 3.3 Key types

- `QueryRun` (name, cypher, params, rows, ms, readonly): one Cypher execution. Every tool returns its `QueryRun`s, so every answer carries its evidence.
- `Highlight` (nodes, edges as `(source_id, target_id, REL_TYPE)`): what the UI lights up for a step.
- `ToolOutput` (summary, data, queries, highlight): the single return type of every tool.
- `Decision` (action `call` or `done`, tool, args, reason, handoff_to): what a role does next. `reason` is shown in the trace as "why".
- `TraceStep` (seq, role, tool, reason, summary, writes, queries, highlight, data): one step of a run, returned to clients and persisted as an `AgentStep` node.
- `CheckFacts` / `Verdict` (`domain/verdict.py`): the input and output of `judge()`.
- `Tool` / `ToolContext` (`agents/registry.py`): a registered tool and the tenant-bound repository it runs against.

### 3.4 The agent loop, step by step

Code: `services/respond.py::respond` and `agents/loop.py::run_role`.

1. `respond(repo, alert_id, llm)` calls the `open_incident` tool. Its query `MERGE`s `(:Incident {id: "inc:<alert suffix>"})-[:TRIGGERED_BY]->(:Alert)`. This node is the board. The step is recorded as step 1 (role `triage`).
2. The current role is `triage`. `run_role()` loops up to `MAX_STEPS_PER_ROLE = 15` times:
   1. Observe: `load_board()` runs the `incident_board` query (RO). It returns the incident, the steps already logged (tool, target, role), the hypotheses with status, source, hops and change time, and the recalled incidents with scores. `cause_service` is derived from the supported hypothesis.
   2. Decide: `llm.decide(role, board, specs)`. With `MockProvider` this is `planner.next_decision(role, board)`, a pure function of the board.
   3. If the decision is `done`: record a step with tool `handoff` and target = the next role (or `human`), and return the next role.
   4. Otherwise act: look up the tool, add `incident_id` to the args if the tool takes one, and call `registry.call()`. This validates the args with the tool's pydantic model and runs it.
   5. Record: append a `TraceStep` whose first query is the `incident_board` read (so the trace shows what the planner saw), then the tool's own queries. `log_step` writes the step as an `AgentStep` node linked by `LOGGED`.
3. `respond()` moves to whatever role the last one handed off to (triage -> investigator -> comms -> none), then builds `outcome()`.

What each role decides, from the board only (`domain/planner.py`):

| Role | Rule (first match wins) |
|---|---|
| triage | `blast_radius` on the alerting service if not run; then `page_on_call` for it; then hand off to investigator. |
| investigator | `recall_similar` if not run. If the best recall score >= 3 and memory not yet used: `hypothesize_from_memory`. If any hypothesis is open: `check_hypothesis` on the first by `check_order` (memory first, then fewest hops, then newest). If one is supported: hand off to comms. If `propose_hypotheses` has not run: run it. Otherwise hand off to comms as a non-change cause. |
| comms | If a cause service is known: `page_on_call` for it, then `blast_radius` for it (who else is at risk). Then `post_update`. Then done (hand to a human). |

The planner branches on query results. An empty `memory_suspects` result sends the investigator to traversal (act 1). A strong recall skips traversal (act 2). Each refutation changes which hypothesis is next. If everything is refuted, it escalates as a non-change cause.

`outcome()` summarises the run for the UI. It collects the checks, runs `recent_changes` once more for the flat baseline, and counts investigator calls and checks. It merges the highlights of the supporting checks into one evidence path.

### 3.5 The tool registry

`agents/registry.py` holds `REGISTRY: dict[str, Tool]`. A tool is a plain function `fn(ctx: ToolContext, args: SomeArgsModel) -> ToolOutput`, registered with `@tool(writes=...)`. The decorator reads three things from the function itself: the name, the docstring (the description agents and MCP clients see), and the pydantic args model from the second parameter (its JSON schema is the tool's input schema). There is no second definition anywhere.

The same registry feeds three surfaces:
- the agent loop: `registry.call(d.tool, ctx, args)`, with `registry.specs()` passed to the planner or LLM;
- the MCP server (`mcp_server/__init__.py::catalogue`): turns every registry tool into an MCP tool, adds a required `tenant` argument and marks read tools with `readOnlyHint`, then adds the two use cases `respond_to_alert` and `reset_tenant`. Calls go to `registry.call()`. See [MCP.md](MCP.md);
- the HTTP API: `GET /api/tools` returns `specs()`, and `POST /api/tenants/{tenant}/tools/{name}` calls `registry.call()`.

Tools at the time of writing (`GET /api/tools` lists the live set). "W" means the tool may write.

| Tool | W | Used by | Named queries (RO = read-only) |
|---|---|---|---|
| `open_incident` | W | `respond()` step 1 | `open_incident` |
| `blast_radius` | W | triage, comms | `incident_head` (RO), `blast_radius` (RO), `record_impacts` (only with an incident) |
| `page_on_call` | W | triage, comms | `incident_head` (RO), `on_call_for` (RO), `record_page` |
| `recall_similar` | W | investigator | `recall_similar` (RO), `record_recalls` |
| `hypothesize_from_memory` | W | investigator | `incident_head` (RO), `memory_suspects` (RO), `add_hypotheses` |
| `propose_hypotheses` | W | investigator | `incident_head`, `path_suspects`, `recent_changes` (RO), `add_hypotheses` |
| `check_hypothesis` | W | investigator | `hypothesis_facts`, `live_paths`, `any_path` (only if no live path), `anomalies_between` (RO), `record_evidence` |
| `post_update` | W | comms | `incident_head`, `update_facts`, `refuted_hypotheses` (RO), `post_update` |
| `resolve_incident` | W | a human (UI, API, MCP, demo) | `incident_head`, `change_info` (RO), `resolve_incident` |
| `dependency_path` | | MCP / API | `live_path` |
| `incident_board` | | MCP / API (the loop calls the same `load_board()` directly) | `incident_board` |
| `who_knows` | | MCP / API (company brain) | `who_knows` |
| `change_story` | | MCP / API (company brain) | `change_story` |
| `service_map` | | API `/graph`, MCP | `service_map` |

`check_hypothesis` is the heart of the investigator. It reads the suspect's facts and up to 20 dependency paths valid at alert time (`live_paths`), then the anomalies on those services between the change and the alert. It judges the path the anomaly lit up most (shortest on ties), so a symptom that travelled a longer path is not misread because the shortest one was quiet. Then it calls the pure `judge()` in `domain/verdict.py`. The rules, in order:
1. The change was rolled back before the alert: refutes.
2. No dependency path valid at alert time from the alerting service to the changed service. If a path exists when you ignore validity, it refutes with "dependency retired". Otherwise it refutes with "no dependency path".
3. The changed service showed no anomaly between the change and the alert: refutes.
4. A service in the middle of the live path showed no anomaly, so the symptom did not travel: inconclusive.
5. Otherwise: supports, with the propagation path as the reason.

Each planted decoy in act 1 is refuted by a different rule: `chg:pricing-2140` by rule 1, `chg:search-420` and `chg:legacy-193` by rule 2 (no path, retired), `chg:cart-310` by rule 3.

### 3.6 Error handling

| Failure | Raised where | What the caller sees |
|---|---|---|
| Unknown alert, incident, hypothesis or change | `ValueError` in tools / `load_board` | API 404 `{"detail": ...}` |
| Unknown tool | `registry.call` (`KeyError`) or the API route | 404 |
| Invalid tool args | pydantic `ValidationError` in `registry.call` | 422 with field-level detail |
| Bad tenant name | `Path(pattern=[a-z0-9_]{1,40})` in the API, `_check_tenant` in the adapter | 422 / `ValueError` |
| Unknown tenant | `tenant_repo` dependency | 404 with a hint to `POST .../reset` |
| FalkorDB down | redis `ConnectionError` | 503. `GET /api/health` still answers with `"falkordb": false`. The store connects on first use, so the app starts without the database. |
| A write sent through `read()` | FalkorDB rejects `GRAPH.RO_QUERY` | exception. This is a programming error, and a test proves it is caught. |
| Planner never finishes a role | `run_role` after 15 steps | `RuntimeError` (500). It guards against a looping LLM. |
| LLM call fails, times out, or picks an unknown tool, bad args or a step already on the board | LLM adapter (`openai_compat.fallback`) | falls back to the deterministic planner's decision for the same board, with the reason prefixed "LLM fallback: ...". The run continues. `resolve_incident` is never offered to the model (human only), and handoffs only go forward. |
| Any error inside an MCP tool call | `mcp_server.build_server` | returned to the client as a tool error; the MCP session stays up |
| Duplicate or missing named query | `queries.all_queries()` at load / `tests/unit/test_catalogue.py` | fails fast in tests, never at runtime |

### 3.7 Concurrency and idempotency

- FalkorDB runs read queries on a graph concurrently and executes write queries on a graph one at a time. Each query is atomic. We rely on this instead of adding our own locks.
- Every write `MERGE`s on a stable id, so repeating it is harmless:
  - ingest: `ingest_*` on `team:`, `person:`, `svc:`, `chg:` and other ids, so re-seeding gives the same node count (tested);
  - `open_incident` on `inc:<alert suffix>`, `add_hypotheses` on `hyp:<incident>:<change>`, `record_evidence` on `ev:...`, `post_update` on `msg:update:<incident>`;
  - edge writers (`record_impacts`, `record_page`, `record_recalls`) use `MERGE ... ON CREATE SET`, so the first writer's properties stick;
  - `resolve_incident` only matches `WHERE i.status <> 'resolved'`, so resolving twice does not count a runbook success twice.
- `log_step` computes `seq = count(existing steps) + 1` inside the same write query that creates the step. Writes on a graph are serialised, so two writers can never get the same `seq`.
- Running `respond()` again on the same alert is safe. The board already shows every tool as done, so each role just hands off. The second run adds `open_incident` and three handoff steps, and no duplicate hypotheses or evidence (tested).
- Known gap: "read the board, decide, write" is not atomic across two responders working on the same incident at the same moment. Because the tools are idempotent, the worst case is a duplicate `AgentStep`, not corrupt state. If it ever matters, add a lease on the incident (see 4.2).
- Different tenants never share a graph, so their writes never wait on each other.

### 3.8 Multi-tenancy

- One FalkorDB instance holds many graphs. Tenant `acme` lives in graph `tenant_acme`. Its pristine copy for demo resets is `pristine_acme`.
- Tenant names must match `[a-z0-9_]{1,40}`. They are checked in the API path and again in the adapter, so a name can never form an unexpected graph key.
- `seed()` loads the synthetic company and then `snapshot()`s it with `GRAPH.COPY`. `reset()` deletes the working graph and copies the pristine one back. If there is no pristine copy, it seeds from scratch.
- A `ToolContext` holds one tenant's repository, and a repository holds one graph handle. A tool has no way to reach another tenant's graph.
- Memory is per tenant: incidents, runbooks and agent history stay in that tenant's graph.

### 3.9 Explainability

- Every `TraceStep` has a `reason` (why the planner chose it), a `summary` (what it found), and every `QueryRun` it ran: the Cypher, params, rows, ms, and whether it was read-only.
- The first query of every non-initial step is `incident_board`, the exact shared state the planner decided from.
- `Highlight` gives the node ids and typed edges to light up. `outcome.highlight` merges the supporting evidence into one path, for example `chg:pgw-pool-1 -CHANGED-> payments-gw <-DEPENDS_ON- payments <-DEPENDS_ON- checkout`.
- The graph keeps the explanation too. Each check leaves an `Evidence` node with its verdict, reason and path. The status update is a `Message` that `CITES` the change, the ticket, the chat and the runbook. The agent history is queryable as `AgentStep` nodes (`GET /api/tenants/{t}/incidents/{id}/steps`).
- The flat baseline is computed for every incident, so every answer comes with "what a change log alone would have blamed".

## 4. Scale and reliability

The demo graph is tiny (25 services). Here is what we would change as each dimension grows, and what already holds.

### 4.1 Bigger graphs (thousands of services, years of changes)

- Index `Change.at` and `Anomaly.at`. Today only `id` is indexed on every label. `GRAPH.EXPLAIN` shows the window filter in `recent_changes` doing a `Node By Label Scan` over all changes. That is fine at 105 changes but not at a million.
- Keep variable-length traversals bounded (`*1..6`, `*0..6` today) and bound `any_path`, which uses an unbounded `shortestPath`.
- Reverse `path_suspects` when the dependency graph is large: start from the few changes in the window and test reachability, instead of expanding every upstream service first.
- Cache the service map per tenant and invalidate on ingest. It changes rarely and the UI asks for it often.
- Archive `AgentStep` nodes of resolved incidents (or keep only a summary). History grows by 12 to 17 nodes per incident in the demo.

### 4.2 Many concurrent incidents

- Per-tenant graphs already shard writes: FalkorDB's one-writer-per-graph rule only serialises writes inside one tenant. Within a tenant each write is small (well under a millisecond of database time here).
- For an alert storm on one tenant: correlate alerts first (one incident for a shared upstream cause) instead of running N investigations. Batch `log_step` writes if they become the bottleneck.
- Add a lease on the incident (for example a `claimed_by` property set by a conditional write) so two responders cannot work the same incident at once.
- Scale reads with FalkorDB replicas. Every read already goes through `GRAPH.RO_QUERY`, so it is safe to route to a replica.
- The app is stateless, so add API replicas freely.

### 4.3 Many tenants

- Restrict each tenant's credentials to its own graph keys with Redis ACLs, as defence in depth on top of the name check.
- Shard tenants across FalkorDB instances by tenant name. The `GraphStore` port is where that routing would live.

### 4.4 LLM cost and latency (when an LLM planner is on)

- Each step is one LLM call, about 17 per incident. Keep the deterministic planner for triage and comms, where the rules are obvious, and use the LLM only for investigator branching.
- Cache decisions by a hash of the board. The same board gives the same decision.
- The deterministic fallback caps the damage of a slow or wrong model: the run always finishes.

### 4.5 Reliability and operations

- Persistence: FalkorDB is Redis, so use RDB/AOF and back up the tenant graphs. Locally, `make db-stop` saves to disk.
- Monitoring: every `QueryRun` carries `ms`, and every `AgentStep` stores `rows` and `ms`. Slow tools can be found with a Cypher query over `AgentStep` nodes. Export the same numbers as metrics when this runs for real.
- Real ingest: deploy webhooks, the paging system and chat would write through the same `ingest_*` `MERGE` queries, so replays and duplicates stay harmless.

## 5. Trade-offs

| Decision | We gain | We give up | ADR |
|---|---|---|---|
| FalkorDB as the only store, one graph per tenant | the graph does the work: traversal, temporal filters, shared state, memory. Tenancy and resets come almost free | no relational store for reporting. Everything is Cypher | [002](decisions/ADR-002-stack.md) |
| Native FalkorDB build (rhel8 module + self-built redis) on the dev machine | works on glibc 2.35 without Docker | the first `make falkordb-bin` compiles redis (a few minutes) | [002](decisions/ADR-002-stack.md) |
| Named `.cypher` files, no OGM | every query is reviewable, documented and parameterised | no compile-time check of query names (a unit test covers it) | [002](decisions/ADR-002-stack.md) |
| Hand-written loop, planner reads the board before every step | the plan lives in the graph, the trace is complete, runs are deterministic | about 2 ms extra per step for the board read. The planner's rules are hand-written heuristics | [003](decisions/ADR-003-agent-loop.md) |
| LLM optional, with a deterministic fallback | works with no key, tests are stable, judges can run it | the default demo does no free-text reasoning | [003](decisions/ADR-003-agent-loop.md) |
| Structural recall instead of vectors | model-free, offline, explainable by a path, respects time | needs a known cause service. Text-only similarity is not captured | [004](decisions/ADR-004-memory-model.md) |
| Memory written only on human-confirmed resolve | the agents cannot reinforce their own mistakes | memory grows only as fast as humans confirm | [004](decisions/ADR-004-memory-model.md) |
| No graph algorithms (`algo.*`) in the core loop | the council judged PageRank on 25 nodes decoration. Bounded traversal, `shortestPath` and temporal predicates do the real work | fewer "algorithm" buzzwords in the demo | [001](decisions/ADR-001-idea.md) |

## 6. What we would revisit as the system grows

1. Range indexes on `Change.at` and `Anomaly.at`, and a reversed `path_suspects` (section 4.1).
2. An incident lease for concurrent responders (section 4.2).
3. Runbook confidence: today `uses` and `successes` only grow, because only confirmed fixes are written. Record failed runbook attempts and decay confidence.
4. Tools register by import side effect: `services/respond.py` imports `services/tools.py` so the `@tool` decorators run. That is simple, but every surface depends on that import. An explicit `register_all()` would be clearer once there are several tool modules.
5. A "no change, it's capacity" path. The investigator already escalates when every change is refuted, but it does not yet look for non-change causes.
6. Vector similarity as a tie-breaker among structurally equal recalls, stored in FalkorDB's own vector index (ADR-004).
7. Real ingest adapters (deploy events, paging, chat) behind the same `MERGE` queries.
